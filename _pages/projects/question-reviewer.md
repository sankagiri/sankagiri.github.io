Build a tool that suggests which multiple-choice questions a teacher should inspect for ambiguity. For example, “Which sorting algorithm is fastest?” is incomplete without assumptions about inputs and what is being measured. A well-posed question can still be difficult, however, and a model can be wrong for reasons unrelated to wording.

Your hypothesis is that disagreement among model answers might help prioritise review. It may turn out to be a poor signal. Finding that out with appropriate controls is a worthwhile project.

**The tool flags candidates for a person to review.** It cannot certify an exam question, infer how students will perform, or decide that an option is a bad distractor simply because models never choose it.

## First session: write six questions and their explanations

Choose a narrow subject you understand, such as basic Python or elementary probability. Write two easy-clear, two hard-clear, and two deliberately ambiguous questions. Each should have four options. Record the intended answer and reasoning. For ambiguous examples, spell out two plausible interpretations and the answers they lead to.

Ask one small model to answer each several times and save the raw outputs. Check that your parser correctly handles missing answers and malformed responses. Repeated answers from one model are repeated samples, not independent test-takers.

**Check before proceeding:** Can you explain the ambiguity without pointing to a model's disagreement? If not, you may only have a hard question or an incorrect key.

## Milestone 1: create human labels before model flags

Build a pilot of around 30–40 questions containing all three groups. Keep a record such as `question_id`, `family_id`, `text`, `options`, `intended_answer`, `clarity_label`, `interpretations`, and `split`. Identify a question and its rewrites as one family.

Ask a second knowledgeable reader to solve and label the questions without seeing your intended category, answer, or model outputs. Discuss disagreements only after recording the independent labels. Mark unresolved cases as uncertain rather than forcing agreement. Deliberately introduced flaws are useful controls, but do not establish performance on naturally occurring exam questions.

Use some families for development and reserve others for evaluation, with each category represented. If you later rewrite a question, it must stay in its family's split. Keep any examples generated by the same template together too.

**Human judgement:** Subject knowledge establishes whether a question admits multiple defensible readings. An AI explanation is a suggestion to inspect, not ground truth. If you cannot find a second reader, keep this as a personal pilot and state the limitation.

## Milestone 2: compare simple review methods

Start with two baselines: random review order, and a single model explicitly asked to identify missing assumptions or competing interpretations. Average the random baseline across several seeded orders. For the single-model baseline, request a fixed ambiguity rating (for example, 0–3) and an explanation citing the wording at issue. Define the rating scale and a fixed tie-breaking rule before ranking questions.

Then try your disagreement signal. Run two or three small models a few times each with recorded sampling settings. A simple score is one minus the fraction of valid answers choosing the most common option. Report invalid responses separately; define a minimum valid-response count before assigning a score. A score based on one remaining valid answer is not reassuring agreement.

Rank questions by the score and inspect the top few. Save prompts, model revisions, outputs, and costs or running time. Do not increase the number of models merely to make the tool look more sophisticated.

**Check before proceeding:** Does the method mostly flag hard-clear questions? Do all models confidently share the same mistaken assumption? Either is evidence about the signal's limitations.

## Milestone 3: evaluate a realistic review budget

On development data, choose a fixed budget, such as reviewing the top five questions. Freeze the scoring method before using the held-out set. Report **precision among those flagged** (how many really are ambiguous), **recall** (how many labelled ambiguities were found), and false alarms on the hard-clear group. Show counts and the number of uncertain labels excluded or analysed separately.

Compare the panel with the single-model reviewer under the same review budget. Inspect missed ambiguities as carefully as the successful flags. A high score on deliberately broken questions is not enough: if possible, add a fresh, independently reviewed sample of questions you have permission to use, without deliberately injecting flaws.

State how the artificial mixture affects your result. A set with one-third ambiguous questions will generally give a different precision from an ordinary exam with few ambiguities. Small held-out samples support a pilot conclusion, not an assurance to a teacher.

## A solid stopping point

A small review interface or report showing the original question, the reason for each flag, and the human verdict; a labelled collection; and a reproducible comparison with both baselines. Include hard-clear false positives and confident missed ambiguities. “The panel adds little beyond one reviewer model” is a perfectly useful finding if the experiment supports it.

Do not collect real student grades or exam responses for the core project. They are not needed to test whether your tool helps identify unclear wording.

## Choose one extension

- Suggest a rewrite for each flagged question, then have humans verify that it removes the ambiguity while preserving the intended concept.
- Study one failure type, such as missing independence assumptions, rather than expanding across many subjects.
- Test whether ranking changes when options are reordered, keeping answer labels correctly mapped.

Only consider claims about student ability or distractor effectiveness in a separate study with appropriate human evidence. Model size and model mistakes are not substitutes for student data.
